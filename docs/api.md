# API — Phase 1 walkthrough (`/v1`)

Base URL locally: `http://127.0.0.1:8200`. Interactive schema: `/docs`
and `/openapi.json` (OpenAPI 3.1, generated by FastAPI).

## Endpoints

| Method | Path | Purpose | Success | Errors |
|---|---|---|---|---|
| POST | `/v1/transcriptions` | upload audio — multipart `file`, optional form `provider` / `language`, optional header `Idempotency-Key` | **201** `JobRecord` + `Location` header | 413 `UPLOAD_TOO_LARGE`, 415 `UNSUPPORTED_MEDIA`, 422 `AUDIO_TOO_LONG` / `PROVIDER_NOT_FOUND` / `VALIDATION_ERROR` |
| GET | `/v1/transcriptions/{id}` | job status / record | 200 `JobRecord` | 404 `JOB_NOT_FOUND` |
| GET | `/v1/transcriptions/{id}/result` | canonical transcript | 200 `TranscriptResult` | 404 `JOB_NOT_FOUND`, 409 `JOB_NOT_READY` |
| POST | `/v1/transcriptions/{id}/retry` | retry a retryable failure | 200 `JobRecord` | 404, 409 `INVALID_TRANSITION` |
| POST | `/v1/transcriptions/{id}/cancel` | reserved | — | **501** `NOT_IMPLEMENTED` (arrives with the async pipeline, Phase 2) |
| GET | `/v1/providers` | providers with capabilities + health | 200 | — |
| GET | `/v1/health/live` | liveness | 200 `{"status":"ok"}` | — |
| GET | `/v1/health/ready` | readiness (PostgreSQL `SELECT 1`) | 200 `{"status":"ready"}` | 503 `{"status":"not_ready"}` |

Phase 1 executes synchronously: by the time POST returns, the job is
already terminal (`SUCCEEDED` or `FAILED`). The URL contract does not
change when Phase 2 moves execution behind Temporal — only the `status`
in the POST response becomes non-terminal.

## Error shape

Every error body:

```json
{"error": {"code": "UNSUPPORTED_MEDIA", "message": "ffprobe rejected the file: ..."}}
```

Pinned mapping: validation → 415/413/422, missing job → 404, not-ready /
conflict / illegal transition → 409, provider failure → 502, anything
unexpected → 500 `INTERNAL_ERROR` (message deliberately opaque).

## Verified real run (2026-10-11, large-v3-turbo on CUDA)

Full raw bodies from this run: `results/phase1_e2e/*.json` (local
artifact, not committed).

```bash
curl -s -F "file=@audio/sample.wav" -F "language=en" \
     -H "Idempotency-Key: e2e-demo-1" \
     http://127.0.0.1:8200/v1/transcriptions
```

- → **201 Created** in 3 s wall; `Location: /v1/transcriptions/aabecb8f-8eca-4734-81de-0af47296ff7c`
- job: `SUCCEEDED`, `actual_provider=faster-whisper`, `model=large-v3-turbo`, `attempt_count=1`
- audio metadata (probed, extension never trusted):
  `wav / pcm_s16le / 16000 Hz / mono / 10.0 s / 320044 B`

Result:

```bash
curl -s http://127.0.0.1:8200/v1/transcriptions/aabecb8f-…/result
```

- `text`: `"Hello, I'm Abdul Javid, AI Engineer at …"` (full text in the file)
- `language: "en"`, `timestamp_granularity: "word"`
- 1 segment, **26 words** with per-word `probability` as `confidence`
- `audio_duration_s: 10.0`, `processing_duration_s: 0.776` → **RTF ≈ 0.078**

## Idempotent clients

Send `Idempotency-Key: <opaque>` on POST:

- replay with the **same audio bytes and parameters** returns the same
  job (same `id`, no re-processing);
- replay of the same key with **different** parameters → 409
  `IDEMPOTENCY_CONFLICT`.

The fingerprint is `sha256` over `(provider, language, options)` + audio
bytes — file names never matter. See `docs/reliability.md` for the exact
semantics and Phase 2 gaps (race-safe insert, expired keys).
